How to turn IBM Bob from a developer tool you open in a terminal into a permanently-running server that accepts API calls, fires scheduled agents, and never sleeps — as long as the VM is alive.

The Core Idea

By default, IBM Bob is an interactive tool: you open a terminal, type a prompt, read the reply, close it. Everything stops the moment you close the session. That model works for individual developers, but it means nothing runs unless you are actively at a keyboard.

The shift to a headless, always-on setup changes that completely:

Interactive Bob (default)
• Lives on your laptop
• Runs only when terminal is open
• One conversation at a time
• Output disappears when session closes
• No external system can call it
• Agents stop when you go to sleep
Headless Bob on a VM (this setup)
• Lives on a cloud VM that never turns off
• Runs 24/7 as a systemd service
• Accepts API calls from anywhere
• Output written to files + Slack + SSE
• Any system can invoke it via HTTP
• Agents fire on schedule while you sleep
⚡

One sentence: Deploy Bob on a VM + wrap it in a FastAPI server + register it as a systemd service = Bob is now an API endpoint that runs forever and can be called by anything, at any time, from anywhere.

Setup in 5 Steps

1
Provision a VM with a persistent disk
Any cloud VM works: Azure, AWS, GCP. Minimum 8 vCPU, 16GB RAM, 100GB disk. We use Azure Standard_D16s_v5 with a 1TB secondary disk mounted at /data/. The VM must have a public IP and open ports 44283, 44285, 44290.
2
Install Bob and set your API key
npm install -g @ibm/bob
Then set the key permanently in the environment:
echo 'export BOB_API_KEY=your_key_here' >> ~/.bashrc && source ~/.bashrc
Verify: bob --version → should print 2.0.0
3
Define your custom modes (agent personas)
Create ~/.bob/settings/custom_modes.yaml with your harness agents. Each mode gets a slug, roleDefinition, and groups: [read,edit,execute,mcp,skill,todo,subtask,subagent,mode]. These are the identities Bob assumes when invoked with bob run --mode <slug>.
4
Deploy the Harness FastAPI server as a systemd service
The Harness server (server.py) wraps Bob in a REST API. Register it as a systemd unit with Restart=always and EnvironmentFile pointing to your .env. Enable it: systemctl enable --now bob-harness. Now Bob is reachable at :44285/jobs forever.
5
Register cron schedules and let it run
POST /schedules with your agent tasks and cron expressions. From this point forward, Bob fires automatically on schedule, writes reports to /data/company/, pushes to Slack, and updates dashboards — with zero human intervention required.

Chapter 01

What is a
Harness Agent?

A foundational concept: what it means to run an AI agent in a harness, why it matters for production systems, and how it differs from interactive use.

Definition

A Harness Agent is an AI language model invoked programmatically — without a human at a keyboard — whose lifecycle (input, execution, output, retry, delivery) is controlled by surrounding orchestration code called the harness.

🤖
The Agent
The AI model that reasons, calls tools, and produces output. In our case: IBM Bob running a specific --mode. Stateless between invocations.
⚙️
The Harness
Orchestration layer managing the agent lifecycle: queues jobs, passes prompts, collects output, handles retries, routes results to downstream systems.
🔁
Non-interactive execution
Agent is called via CLI (bob run "prompt") or REST API. No human approves tool calls at runtime — all permissions are pre-granted by the harness.
📋
Structured output
The harness parses agent output into structured data (JSON, files, DB records) that other systems consume — not just raw text for a human to read.

💡

Key insight: The Harness is the universal adapter. Any system that can send an HTTP request can trigger a Bob agent — including GitHub Actions and CI/CD pipelines. Any system that can receive an HTTP call, a git push, or an oc command can be a target — including OpenShift clusters. And every agent run feeds back into memory management via Obsidian MCP, so the loop compounds: each run makes the next one smarter.

1
Trigger
Something external initiates the agent: a cron schedule, an API call, a Slack message, a CI pipeline step, or a user action on a dashboard.
2
Harness receives and queues
Validates the request, creates a job record, queues it. Manages concurrency and timeouts. Caller gets a job ID immediately and polls for status.
3
Agent executes
Harness spawns bob run --mode <mode> "prompt" as a subprocess. Bob runs headlessly with no human approval needed.
4
Harness delivers result
Captures stdout, extracts the reply, updates job status, and delivers to files, Slack, dashboards, or SSE streams.
💡

The term "harness" comes from software testing — a test harness is scaffolding that runs code automatically. A harness agent applies the same idea to AI: the harness runs the AI automatically, captures its output, and delivers the result.

Positioning IBM Bob
as a Harness Agent

How Bob's non-interactive CLI, custom modes, and tool system make it an ideal harness agent — and exactly where the harness boundary sits.

Bob's Non-Interactive Mode

IBM Bob ships with a bob run subcommand that is the foundation of every harness integration:

# Basic prompt
bob run "Summarise /data/company/intel-report.md"

# With a specific mode
bob run --mode intel-agent "Research IBM AI coding competitors"

# Structured JSON output -- ideal for scripting
bob run --format json --mode ops-agent "Check system health" > result.json

# NDJSON stream -- process events in real time
bob run --format stream-json --mode dev-agent "Audit the codebase" \
  | grep '"type":"result"' | jq '.last_message'

# Cap cost and turns for automated workflows
bob run --max-cost 0.50 --max-turns 20 --mode ceo-agent "Generate board report"
✅

All tools are pre-approved when running non-interactively with bob run. Bob reads files, executes shell commands, calls MCPs, and writes output without pausing for permission.

Custom Modes as Agent Personas

roleDefinition
System prompt injected before every run. Defines who the agent is, what it knows, how it behaves. Encodes domain expertise.
groups
Tool permission groups: read, edit, execute, mcp, skill, todo, subtask, subagent, mode. A harness agent gets all nine.
whenToUse
Short user-facing description shown in dashboard UIs and used by CEO agent routing logic.
slug
Identifier passed to bob run --mode <slug> and to the harness REST API as the mode field.
# ~/.bob/settings/custom_modes.yaml
customModes:
  - slug: intel-agent
    name: Intel Agent
    whenToUse: "Web research, competitor scraping, market intelligence, live news."
    groups: [read, edit, execute, mcp, skill, todo, subtask, subagent, mode]
    roleDefinition: |
      You are the Intel Agent -- a specialized market intelligence operative
      with live internet access via Firecrawl MCP.
      Always write findings to /data/company/intel-report.md

Output Parsing — Critical Detail

# Bob stdout structure (pretty mode)
------------------------------------------------  <-- U+2500 box-drawing char (NOT ASCII -)
Assistant (1) 2026-09-05 17:47:00 UTC (+32s)
------------------------------------------------

  [actual reply -- may contain markdown, ---, tables, code blocks]

------------------------------------------------  <-- end of reply
Task Summary
Total Cost: 0.101
⚠️

Critical: Bob separators use Unicode U+2500 box-drawing character, not ASCII hyphen. Agent replies often contain markdown --- dividers. If your parser matches on any hyphen-run it will truncate replies mid-content. Only break on the U+2500 character. Use --format json to skip parsing entirely.

Loop Engineering — Self-Healing

def run_agent_with_retry(prompt, mode, max_retries=2):
    for attempt in range(max_retries + 1):
        job = start_job(prompt if attempt == 0 else retry_prompt, mode)
        status, output = poll_job(job["id"])
        if status == "completed" and output.strip():
            return output  # success
        retry_prompt = (
            f"SELF-HEALING RETRY (attempt {attempt+1}):\n"
            f"Previous run failed: {output[:400]}\n\n"
            f"Original task: {prompt}\n\nAnalyse and complete the task."
        )

OpenHarness is a great framework for building agents from scratch. But IBM Bob is a fully matured, enterprise-grade agent that comes with everything wired up before you write a single line of harness code. Here's what that means in practice:

💼
Enterprise-grade out of the box
IBM Bob ships with SSO, audit logging, data residency controls, and IBM security review — none of which you get from open-source frameworks. An enterprise can deploy Headless Bob without a 6-month security review process.
🧠
Custom modes = zero-config agent personas
Define a CEO agent in 10 lines of YAML. No Python class, no constructor, no tool registration loop. bob run --mode ceo-agent "prompt" and it's running with full domain expertise injected via roleDefinition.
🔧
43+ tools pre-wired
File read/write, shell exec, web search, MCP protocol, skills loading — all available with zero setup. OpenHarness ships 43 tools too, but you have to build the harness layer yourself. Bob's tools are ready in groups: [read,edit,execute,mcp,skill].
📦
MCP ecosystem, natively
Bob runs Firecrawl, Obsidian, Postgres, MongoDB, Redis MCPs with a single JSON config. Intel Agent gets live internet access; Dev Agent gets database access — no custom integration code needed.
🔁
Non-interactive mode is first-class
bob run is designed for headless execution. Output is structured and parseable. JSON and stream-json output formats remove the need for fragile stdout parsing. The harness just calls Bob and reads the result.
📋
Skills = reusable agent knowledge
SKILL.md files give agents persistent, specialised knowledge loaded on demand — market intelligence playbooks, coding standards, ops runbooks. No vector database, no RAG pipeline. Just markdown files that Bob reads when relevant.
🎯

The key insight: OpenHarness makes it possible to build an agent runtime. IBM Bob means you already have one. The harness layer (our FastAPI server + scheduler) is thin because Bob handles everything the agent actually needs to do.

Bob + Harness: What OpenHarness Does That We Should Borrow

OpenHarness has 15k+ stars because it solves real problems. Here are the 4 patterns from OpenHarness that would meaningfully upgrade Headless Bob if added to the Harness layer:

IMPROVEMENT 01 — HIGH VALUE
ohmo as inbound Slack / Telegram gateway
OpenHarness's ohmo has a battle-tested Slack/Telegram/Discord gateway. Headless Bob is stuck at outbound-only Slack because IBM workspace blocks xoxb- bot tokens. Wiring ohmo as a relay between Slack and our HQ /api/chat endpoint would unlock true two-way conversation — type a question in Slack, CEO agent replies there automatically. No IBM workspace permissions needed; ohmo runs outside IBM's tenant.
IMPROVEMENT 02 — HIGH VALUE
Persistent memory between agent runs (MEMORY.md pattern)
OpenHarness agents write key decisions, patterns, and context to a MEMORY.md file that is injected at the start of every subsequent run. Right now, each Bob job starts cold — the intel agent re-discovers the same competitors every day. A /data/company/MEMORY.md that accumulates context across runs would make agents measurably smarter over time with zero infrastructure cost.
IMPROVEMENT 03 — MEDIUM
OpenHarness swarm registry as the orchestration backbone
Our CEO agent delegates via raw curl POST /jobs inside a Bob prompt. OpenHarness's swarm module provides a proper team registry, mailbox-based message passing, and a background task lifecycle manager. Using it as the coordination layer instead of ad-hoc curl calls would give us structured agent-to-agent communication, parallel delegation, and proper task state management — with the Bob binary still doing the actual agent work.
IMPROVEMENT 04 — MEDIUM
autopilot-dashboard as a polished React frontend
OpenHarness ships an autopilot-dashboard (React + TypeScript + Vite) that visualises agent runs in real-time. Our HQ dashboard is Flask + vanilla JS — functional but not demo-worthy at scale. Embedding autopilot-dashboard and wiring it to our SSE event bus (/api/events) would give the HQ a production-quality frontend with near-zero custom CSS work.

Pattern via Harness REST (curl from cron)

# Submit to Harness, poll for completion, log output
# Save as /usr/local/bin/bob-intel-cron.sh
#!/bin/bash
set -e
HARNESS="http://localhost:44285"
PROMPT="Research AI coding tools news from past 24h. Write to /data/company/intel-report.md"

JOB_ID=$(curl -sf -X POST $HARNESS/jobs \
  -H "Content-Type: application/json" \
  -d "{"prompt":"$PROMPT","mode":"intel-agent"}" \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['id'])")

echo "[$(date -u)] Job submitted: $JOB_ID"

# Poll until done (max 10 min)
for i in $(seq 1 120); do
  STATUS=$(curl -sf $HARNESS/jobs/$JOB_ID \
    | python3 -c "import sys,json; print(json.load(sys.stdin)['status'])")
  [ "$STATUS" = "completed" ] && echo "DONE" && exit 0
  [ "$STATUS" = "failed" ]    && echo "FAILED" && exit 1
  [ "$STATUS" = "timeout" ]   && echo "TIMEOUT" && exit 1
  sleep 5
done
echo "POLL TIMEOUT"

# Register in crontab:
# 0 7 * * * /usr/local/bin/bob-intel-cron.sh >> /var/log/bob-intel.log 2>&1

as Persistent Memory

How Headless Bob uses a local Obsidian vault connected via MCP to accumulate knowledge across runs — giving agents a persistent, structured long-term memory that survives restarts, scales over time, and is human-readable.

The Problem: Agents Start Cold

By default, every Bob agent job starts with zero memory of what happened before. The Intel Agent discovers the same competitors every morning. The Ops Agent flags the same recurring issue it already flagged yesterday. The CEO Agent re-learns the company context from scratch every time it runs.

⚠️

Without persistent memory: Each job is an island. Agents duplicate work, miss patterns, and cannot learn from previous runs. A 30-day-old system is no smarter than a 1-day-old system.

The Solution: Obsidian MCP as a Memory Layer

The Obsidian MCP server connects Bob directly to a local vault of markdown notes. Agents can read, write, search, and update notes programmatically — turning the vault into a structured, queryable, human-readable long-term memory store.

📖
Read existing notes
Before starting a task, an agent reads relevant vault notes to load context: previous findings, known issues, decisions made, patterns observed.
✏️
Write new findings
After completing a task, the agent writes key insights and new patterns to the vault. Future runs inherit this accumulated knowledge.
🔍
Search across history
Agents can search_notes by keyword or tag to find relevant context from any past run — not just yesterday, but months ago.

Chapter 09

Agent Rerouting
& Parallel Execution

How IBM Bob's Harness enables dynamic agent rerouting at runtime and parallel multi-agent execution — so a single CEO question can simultaneously fan out to multiple specialists and synthesize their results into one answer.

Two Problems, One Harness Solution

🔀
Without rerouting
Agent picks wrong specialist. CEO sends a code question to Intel Agent. Intel returns irrelevant market data. User gets a wrong answer. No recovery path — the job just fails silently.
⏳
Without parallel execution
CEO delegates to Intel, waits 60s, then delegates to Ops, waits another 60s. Total latency: 2+ minutes for a question that could have been answered in 60s with parallel runs.

Pattern 1 — Agent Rerouting

The CEO agent inspects every incoming question and dynamically routes it to the most appropriate specialist — or routes to multiple specialists if the question spans domains. If the first agent's output is empty or off-topic, the harness re-routes to a fallback agent automatically.

Agent Rerouting Flow

Routing Logic in the CEO Agent Prompt

# ceo-agent roleDefinition (excerpt)
You are the CEO Agent. For every question:

1. CLASSIFY the question domain:
   - market/competitors/news   → delegate to intel-agent
   - infrastructure/services   → delegate to ops-agent
   - code/build/deploy         → delegate to dev-agent
   - broad/cross-domain        → delegate to ALL THREE in parallel

2. DELEGATE by submitting jobs to the Harness API:
   curl -s -X POST http://localhost:44285/jobs      -d '{"prompt":"...","mode":"intel-agent"}'

3. POLL each job until completed or failed

4. If a job returns empty output:
   - Re-route same task to a different agent (fallback)
   - Or re-submit to same agent with error context (self-heal)

5. SYNTHESIZE all results into one board-level answer

Rerouting on Failure

# From app.py -- rerouting when ops-agent returns empty
if not ops_out.strip():
    yield send("loop_retry", {"agent": "ops", "attempt": 1})
    # Re-route: retry with self-healing prompt
    retry_job = start_job(
        f"SELF-HEALING RETRY: previous run failed.
"
        f"Error: {raw_output[:400]}

"
        f"Original task: {message}

"
        f"Analyse the error and complete the task.",
        "ops-agent"
    )
    ops_out = poll_until_done(retry_job["id"])

Pattern 2 — Parallel Agent Execution

The CEO agent submits multiple jobs simultaneously to the Harness /jobs API — one per specialist agent — then polls all of them concurrently. Intel and Ops run at the same time. Total latency = max(individual runtimes), not sum.

Parallel Execution Timeline

Parallel Submission in Code

# Submit all specialist jobs simultaneously
intel_job = start_job("Research IBM competitors vs GitHub Copilot", "intel-agent")
ops_job   = start_job("Check infrastructure health and service status", "ops-agent")
dev_job   = start_job("Review recent code changes and flag risks", "dev-agent")

# Poll all three concurrently (non-blocking loop)
jobs = {
    "intel": intel_job["id"],
    "ops":   ops_job["id"],
    "dev":   dev_job["id"]
}
results = {}
while len(results) < len(jobs):
    for name, job_id in jobs.items():
        if name in results:
            continue
        resp = get_job_status(job_id)
        if resp["status"] in ("completed", "failed", "timeout"):
            results[name] = resp.get("output", "")
    time.sleep(3)

# CEO synthesizes all three results
intel_out = results["intel"][:2000]
ops_out   = results["ops"][:1000]
dev_out   = results["dev"][:1000]
synthesis = f"Intel: {intel_out}\nOps: {ops_out}\nDev: {dev_out}"
ceo_reply = invoke_bob(synthesis + "\n\nSynthesize into board-level summary.", "ceo-agent")

Pattern 3 — Conditional Rerouting Tree

More advanced: the CEO agent builds a decision tree at runtime. Depending on what the first agent returns, it may trigger a second round of delegation to a different specialist.

Conditional Rerouting Tree

Live Config: BOB_MAX_JOBS

The Harness server controls how many Bob subprocesses can run simultaneously via the BOB_MAX_JOBS environment variable:

# /data/bob-harness/.env
BOB_MAX_JOBS=200          # up to 200 parallel Bob jobs on this VM
BOBSHELL_API_KEY=...      # maps to BOB_API_KEY for each subprocess
BOB_MODE=unrestricted-dev # default permission mode
💡

On this VM (Standard_D16s_v5): 16 vCPUs, 64GB RAM. With BOB_MAX_JOBS=200, the Harness can run up to 200 parallel Bob agent jobs. In practice, 3–5 run simultaneously during a CEO delegation cycle. The VM has headroom to scale to dozens of concurrent agents.
